# Local Model: เชื่อมตัวกรองคำตอบ

วันที่พัฒนาและทดสอบ: 18 พฤศจิกายน 2026

## สถานะและขอบเขต

ต่อ `src/lib/ai/localReplyGuard.ts` เข้ากับ `tests/eval/runTurn.ts` ก่อนส่งร่างคำตอบให้วงจร grounding เดิมแล้ว ใช้เฉพาะชุดประเมิน local ไม่เปลี่ยนเส้นทาง production ไม่อ่านฐานข้อมูลจริง ไม่สร้างออเดอร์ และไม่ deploy

```text
ข้อมูลร้านจำลอง → ค้นสินค้าตามสิทธิ์ → โมเดลร่างคำตอบ
  → ตัวกรองคำตอบ → grounding เดิม → คำตอบสุดท้าย + รายงาน
```

- หลังอ่านแคตตาล็อก ยอมรับเฉพาะข้อความที่ตรงกับแม่แบบจากข้อมูลที่ตรวจสอบแล้ว มิฉะนั้นแทนด้วยแม่แบบชื่อ ราคา และสต๊อก ไม่ยกคำสัญญาหรือโปรโมชั่นจากร่างโมเดลมาใช้
- หลักฐานต้องตรงร้านปัจจุบัน ตรวจจำนวนรายการ ชนิดข้อมูล ราคา สต๊อก และชื่อสินค้า หากหายหรือผิดรูปแบบ ใช้ข้อความแจ้งว่ายังยืนยันไม่ได้
- ใช้ผลอ่านแคตตาล็อกครั้งล่าสุดในเทิร์น รวมถึงเมื่อโมเดลเรียกค้นใหม่ ไม่ใช้ cache ข้ามคำขอ
- ไม่พบสินค้าให้ขอชื่อหรือรุ่นเพิ่ม ไม่เลือกสินค้ารายการแรกแทน ปรับถ้อยคำถามต่อไม่ให้ grounding เดิมตีความคำขอรหัสสินค้าเป็นการอ้าง SKU ที่ไม่มีหลักฐาน
- ร่างที่ว่าง ถูกตัดกลาง หรือมีอักษรนอกภาษาที่รองรับ ไม่ถูกส่งเป็นคำตอบดิบ หากแคตตาล็อกถูกต้องยังสร้างแม่แบบตอบได้
- เมื่อไม่มีการอ่านแคตตาล็อก เช่น คำทักทายหรือร้าน Q&A มีขอบเขต `language_only` เท่านั้น ไม่รับรองข้อเท็จจริงหรือนโยบายร้าน และยังผ่าน grounding เดิม

## การเปิดใช้งาน

`npm run eval:local` เปิด `EVAL_LOCAL_REPLY_GUARD=1` เป็นค่าเริ่มต้นร่วมกับ Ollama, `read_only` และ catalog prefetch ค่าที่ไม่ใช่ `0` หรือ `1` และการเปิดกับ cloud/full profile/ไม่มี prefetch จะหยุดก่อนเรียกโมเดล

ปิดเพื่อเปรียบเทียบกับ baseline ใน PowerShell:

```powershell
$env:EVAL_LOCAL_REPLY_GUARD='0'
npm run eval:local
Remove-Item Env:EVAL_LOCAL_REPLY_GUARD
```

หากปิด prefetch หรือเปลี่ยนเป็น full profile ต้องปิดตัวกรองด้วย ไม่ได้เปลี่ยนตัวเชื่อม production ให้ใช้ local

## ความหมายของรายงาน

JSON ระบุ `localReplyGuard` และผลแต่ละข้อใน `replyGuard`: แหล่งคำตอบ (`model`, `catalog_template`, `safe_notice`), เหตุผล, ขอบเขต และการยอมรับร่าง แยก `model_draft` ออกจาก `assistant` ในบทสนทนา Markdown ระบุจำนวนร่างที่ถูกแทน

คะแนนยังตรวจร่างโมเดลเดิมด้วย ไม่ให้แม่แบบที่ถูกต้องกลบข้อผิดพลาดของโมเดล การผ่านหนึ่งข้อไม่รับรองทั้งระบบหรือความพร้อม production

## ผลตรวจยืนยัน

- ชุดทดสอบเฉพาะส่วน 47 ข้อผ่าน รวม 10 ข้อใหม่สำหรับตัวกรองและการเชื่อมต่อ
- ชุดทดสอบทั้งหมด 238 ข้อผ่าน ตรวจ TypeScript และ ESLint เฉพาะไฟล์ที่แก้ผ่าน
- ทดลอง Ollama `qwen3.5:4b` บนเครื่องจริงด้วยข้อมูลร้านจำลอง `price_stock-01`: ผ่าน 1/1 ใช้เวลารอโมเดลประมาณ 10.5 วินาที ตัวกรองแทนร่างด้วยแม่แบบ 1 ครั้ง ไม่มี cloud judge
- ขยายชุดทดสอบด้วยเคสหลายสินค้า/หลายเทิร์นในร้านเดียวกัน (`price_stock-10`, `price_stock-11`, `product-09`) เพื่อตรวจว่าเทิร์นที่สองไม่หลุดใช้ราคา/สต๊อกจากเทิร์นก่อนหน้า พบบั๊กใน mock ของชุดทดสอบ offline เอง (`offlineDraft` ใน `tests/eval/runTurn.ts`) ที่ไล่หาชื่อสินค้าจากทุกเทิร์นรวมของเก่า ไม่ใช่แค่คำถามล่าสุด ทำให้ร่างจำลองหลุดพกราคาสินค้าตัวแรกติดมาด้วย แก้แล้วให้ใช้คำถามล่าสุดเท่านั้น ไม่กระทบโค้ด production เพราะเป็นมอคของชุดทดสอบ
- ทดลอง Ollama `qwen3.5:4b` จริงกับ `price_stock` ทั้งหมด (11 ข้อ ครอบ 3 ร้าน) และ `product` ทั้งหมด (9 ข้อ ครอบ 3 ร้าน) รวมเคสหลายเทิร์นข้างบน: ผ่าน **20/20** ตัวกรองแทนร่างโมเดลด้วยแม่แบบแทบทุกข้อ (20/20) เพราะร่างจริงของโมเดลใช้คำพูดต่างจากแม่แบบที่ตรวจสอบแล้วเล็กน้อยเสมอ ถือว่าตัวกรองทำงานตามที่ออกแบบ (เลือกความปลอดภัยมากกว่าคำตอบดิบของโมเดล) แต่หมายความว่าคำตอบจริงจะได้น้ำเสียงจากแม่แบบ ไม่ใช่น้ำเสียงโมเดล จนกว่าจะปรับแม่แบบหรือเกณฑ์ตรวจให้ยืดหยุ่นขึ้น

## ส่วนอ่านแคตตาล็อกจริง (ยังไม่ต่อ production)

เดิม `prefetchCatalog` (`src/lib/ai/catalogPrefetch.ts`) ใช้ได้กับ fixture เท่านั้น เพิ่มส่วนที่ทำให้ใช้กับข้อมูลร้านจริงได้โดยยังไม่เปิดใช้กับลูกค้าจริง:

- `src/lib/ai/toolDispatcher.ts`: `search_products` และ `check_stock` คืน `catalogSnapshot` (shopId + รายการ id/name/price/stock สูงสุด 5 แถว) จากแถวที่ query กรองด้วย `eq('shop_id', shopId)` ไปแล้ว ไม่ได้เพิ่มช่องทางตรวจสิทธิ์ใหม่ ใช้ query เดิมที่ enforce shop_id อยู่แล้ว (RLS ของ anon-key client + filter ชัดเจน)
- `src/lib/ai/catalogPrefetchAdapter.ts` (ใหม่): ตัวเชื่อม `execute` ให้ `prefetchCatalog` เรียก `executeTool` จริงแทน fixture ตรวจซ้ำว่า `scope.shopId` ตรงกับ shop ที่ active อยู่ใน context ก่อนยิง query ทุกครั้ง ถ้าไม่ตรงจะ throw ก่อนแตะฐานข้อมูล
- ยังไม่เรียกใช้ใน webhook หรือเส้นทางแชทลูกค้าจริง เป็นโมดูลที่สร้างและทดสอบแยกไว้ก่อน
- ทดสอบใหม่ `tests/catalogPrefetchAdapter.test.ts` (4 ข้อ ผ่านทั้งหมด): จำลองฐานข้อมูลที่มีสินค้าชื่อเดียวกันจากร้าน A และ B ปนกัน ยืนยันว่า `search_products`/`check_stock` คืนเฉพาะแถวร้านตัวเอง, ขอ scope ร้านอื่นถูกปฏิเสธก่อนยิง query, และ `prefetchCatalog` แบบ end-to-end กับ 2 ร้านพร้อมกันไม่ข้ามร้าน
- ชุดทดสอบทั้งหมดรวมของใหม่ **242/242** ผ่าน TypeScript และ ESLint ผ่าน (มีแต่ warning เดิมของไฟล์ที่ไม่ได้แก้)

## ทดสอบกับร้านจริง JackShop (อ่านอย่างเดียว ยังไม่ต่อ production)

ได้รับอนุญาตให้ใช้ร้านทดสอบ **JackShop** ของจริงใน Supabase ทดสอบ `catalogPrefetchAdapter` กับข้อมูลจริง สร้างสคริปต์แยก `scripts/catalog-shadow-check.ts` (ไม่แก้ `salesAgentEngine.ts` ที่เป็นเส้นทางลูกค้าจริง):

- ใช้ `supabaseAdmin`/`supabase` อ่านอย่างเดียว (`select`/`ilike`) หา shop และสินค้าตัวอย่างของ JackShop เท่านั้น ไม่มี insert/update/delete
- เรียก `createCatalogPrefetchExecutor` พร้อม `dryRun: true` เหมือนที่ `createShadowExecutor` ใช้ในระบบจริง เพื่อข้ามการเขียน sales_stage ใน `toolDispatcher.ts` ยืนยันก่อนรันว่า handler ของ `search_products`/`check_stock` เป็น select ล้วน และเส้นเขียนเดียวที่มีถูก guard ด้วย `!ctx.dryRun` อยู่แล้ว
- รันคำถาม 3 แบบ: ถามสินค้าทั้งหมด (`มีสินค้าอะไรบ้างคะ`) และถามสินค้าจริง 2 ชิ้นของร้านด้วยประโยคธรรมชาติ (`<ชื่อสินค้า> ราคาเท่าไหร่คะ`)
- ผล: คำถามแบบรายการสินค้าทั้งหมดทำงานถูกต้อง (`search_products` คืน 5 รายการ ตัวกรองแทนด้วยแม่แบบตามปกติ) แต่คำถามแบบธรรมชาติที่ถามสินค้าเจาะจง **ไม่พบสินค้าเลยทั้ง `search_products` และ `check_stock`** แม้สินค้านั้นมีอยู่จริงในร้าน
- สาเหตุ: `prefetchCatalog` (`src/lib/ai/catalogPrefetch.ts`) ส่งทั้งประโยคของลูกค้าเป็นคำค้นตรงๆ (`keyword`/`product_name` = ข้อความทั้งหมด) แล้ว `applyProductSearchFilters` ใน `toolDispatcher.ts` ใช้ `ilike '%ทั้งประโยค%'` จับคู่กับชื่อสินค้า เมื่อประโยคมีคำถามต่อท้าย เช่น "ราคาเท่าไหร่คะ" ชื่อสินค้าจริงจะไม่ตรงกับทั้งประโยคจึงหาไม่พบ ไม่ใช่บั๊กของ adapter ใหม่ แต่เป็นข้อจำกัดเดิมของตัว prefetch ที่ชุดทดสอบ eval ไม่เคยเจอ เพราะคำถามในชุด fixture ส่วนใหญ่สั้นใกล้เคียงชื่อสินค้าอยู่แล้ว
- ผลกระทบจริงยังจำกัด เพราะเส้นทางที่ใช้งานอยู่ตอนนี้ (eval/production) โมเดลยังเรียก `search_products` ของตัวเองซ้ำได้ด้วยคำค้นที่ฉลาดกว่าถ้า tool profile อนุญาต ซึ่งจะอัปเดต evidence ให้ใหม่ แต่ระบบ prefetch ที่ตั้งใจให้ตรวจ "ก่อน" โมเดลตอบ จะยังเห็นแคตตาล็อกว่างในตาแรกจากคำถามธรรมชาติแบบนี้
- ยังไม่ได้แก้ไขตรรกะการค้นใน `catalogPrefetch.ts`/`applyProductSearchFilters` เพราะกระทบโค้ดที่ชุดทดสอบเดิม 47+ ข้อผูกไว้ รอให้คุณตัดสินใจก่อนว่าจะปรับคำค้นให้ตัดคำถามท้ายประโยคออกก่อนส่งเข้าค้นหรือไม่

## แก้คำค้นให้ทนคำถามท้ายประโยค (ยืนยันกับ JackShop จริงแล้ว)

เพิ่ม `extractSearchKeyword()` ใน `src/lib/ai/catalogPrefetch.ts` ตัดเฉพาะวลีคำถามเรื่องราคา/สต๊อกที่ไม่กำกวมท้ายประโยค (`ราคาเท่าไหร่`, `เท่าไหร่`, `เหลือกี่...`, `กี่บาท`, คำลงท้ายสุภาพ `คะ/ครับ/ค่ะ`) ก่อนส่งเป็น `keyword`/`product_name` **ไม่ตัดคำว่า "ไหม" เดี่ยวๆ** เพราะเป็นส่วนหนึ่งของชื่อสินค้าจริงได้ (เช่น "ผ้าพันคอไหม") และไม่ตัดคำนำหน้าประโยค ("แล้ว", "มี") เพราะเสี่ยงตัดข้อความที่มีความหมายออกโดยไม่ได้ตรวจสอบเพียงพอ — เป็นการแก้เฉพาะกรณีที่พิสูจน์แล้วจากข้อมูลจริง ไม่ใช่การเขียนคำค้นใหม่ทั้งหมด

ยืนยันผลด้วยสคริปต์เดิม `scripts/catalog-shadow-check.ts` กับร้าน JackShop จริงอีกรอบ: คำถาม "กางเกงยีนส์ขาม้า ราคาเท่าไหร่คะ" และ "กระเป๋าสะพายหนัง PU ราคาเท่าไหร่คะ" ซึ่งก่อนแก้หาสินค้าไม่พบเลย ตอนนี้ `search_products`/`check_stock` เจอสินค้าถูกต้อง 1 รายการทั้งคู่

อัปเดตชุดทดสอบเดิม 2 จุดใน `tests/catalogPrefetch.test.ts` ที่ยึดพฤติกรรมเดิม (คำค้น = ประโยคทั้งหมดไม่ตัดอะไร) ให้ตรงกับพฤติกรรมใหม่ (ตัดคำลงท้ายสุภาพแล้ว) ชุดทดสอบทั้งหมดรวมใหม่ **242/242** ผ่าน TypeScript และ ESLint ผ่าน

งานถัดไปที่ยังเปิดอยู่: (1) คำนำหน้าประโยค ("แล้ว", "มี") ยังไม่ได้ตัด เพราะยังไม่ได้พิสูจน์ด้วยข้อมูลจริงว่าปลอดภัย เป็นข้อจำกัดที่เหลืออยู่ของ `prefetchCatalog` (2) พิจารณาว่าจะปรับแม่แบบ/เกณฑ์ตัวกรองให้คำตอบที่ผ่านดูเป็นธรรมชาติขึ้นหรือไม่ ทั้งสองยังไม่ได้ทำ รอความเห็นคุณก่อน
