# DealMee audit — 2026-10-31

Scope: commits `3eb9c69` (block greeting-only handoff) through `9608822` (docs: update help guide) on `main`, plus the fixes in this pull request.

## Overall verdict

**Not production-ready as pushed.** Typecheck, tests, and a webpack production build succeed, and the new shop APIs are authenticated. Several features are only half wired, and a handful of bugs were real: the bot offered cash on delivery with the shop switch off, an unreadable slip on a pending order never alerted the shop, the response cache could replay price/stock/order answers and other customers' later turns, sample orders still landed in revenue, and telemetry tables let a signed-in shop insert fake analytics.

This pull request fixes those clear bugs. It does not finish the unfinished dashboards, Rich Menu postback, or shadow-eval design. Those need an owner decision.

## Auth and isolation

Every new route under `src/app/api/shop/**` calls `requireShop()` and uses the session shop id. `POST /api/cron/follow-up` requires `Authorization: Bearer ${CRON_SECRET}` and returns 503 when the secret is unset. LINE still rejects a missing or bad `x-line-signature`. Facebook still checks `verifyFacebookSignature`.

New tables enable RLS and scope rows with `shop_id IN (SELECT workspace_id FROM public.users WHERE id = auth.uid())`, which matches the rest of this schema. Service-role RPCs `set_conversation_outcome`, `record_skill_exposure`, and `increment_memory_usage` are revoked from `anon` and `authenticated`.

## Issues

### Fixed in this PR

1. **High — COD ignored `shops.cod_enabled`.** The sales prompt and `take_order` treated เก็บปลายทาง as always available. Prompt lines now follow the checkbox, and `take_order` refuses a COD order when the switch is off. Payment instructions after an order do the same.
2. **High — unreadable slip on a pending order did not alert the admin.** The customer got a failure message and the function returned. The admin is now notified, on both LINE and Facebook (shared `settleSlipImage`). Slip-to-Record failures notify as well.
3. **High — response cache could serve stale or cross-turn answers inside a shop.** Guarded as described above. Cross-shop keys were already separated by `shop_id`.
4. **High — signed-in users could insert `skill_exposures`, `tool_usage_log`, and `shop_skill_revisions`.** Policies allowed any non-anon role. Inserts are service-role only. The conversion view counted `outcome = 'paid'`, which the check constraint never allows, so the rate was always 0. It now counts `conversion`. Views are `security_invoker`.
5. **Medium — Slip-to-Record could insert the same `trans_ref` twice, ignored the shop slip provider, and stored `conversation_id` as null.** Deduped in code and with a unique index. Uses `features.slip_verification`. Looks up the LINE conversation.
6. **Medium — back-in-stock give-up copy and filter injection.** Message uses the asked-for product. Name is not spliced into a PostgREST `or` string.
7. **Medium — sample data in a live shop.** Seed action, products button, metric filter, and fake admin audit rows.
8. **Medium — BYOK Gemini key in the validate URL.** Sent as a header; provider errors are redacted.
9. **Low — skill rollback left cached answers in place.** Cache for that shop is deleted.
10. **Low — lint errors** from a variable named `module` in three test files.
11. **Low — batch skill extract and shadow eval queried columns that were never created.** Queries use `set_at` and the first customer message.

### Needs an owner decision

1. **Slip-to-Record replaces order verification** for the same LINE image. Confirm/reject does not pay an order. Should a shop be able to run both?
2. **Rich Menu is an API with no screen and no postback handler.** Creating one also does not upload the 2500×843 image. LINE allows a limited number of rich menus per channel; this route does not check that quota.
3. **Sidebar.** Agent memory, tool analytics, cost monitor, slip transactions, and skill revisions exist as URLs and are not in `src/lib/dashboard/nav.ts`.
4. **Shadow eval** is a local heuristic stored as agent memory, not a second model answer. The API has no button.
5. **Turn feedback and batch extract** have APIs and no product UI.
6. **Agent memory is not learned from chats.** Only manual rows are injected.
7. **Cost monitor** is a flat $0.0001 times message count, not provider token cost.
8. **COD fee** (`cod_fee_*`) is saved in settings and is not added in `computeShippingFee`. Live Studio still mentions COD without reading `cod_enabled`.
9. **Back-in-stock push** does not consult the LINE push quota before sending. It does use the per-shop token.
10. **Telemetry and retrieval** stay off unless the env flags are set, even after the shop turns skills on.
11. **`npm audit` upgrades**, especially a `next` bump, were not done. The critical Next advisory is Windows-hosted RCE; confirm before changing the framework version on Vercel.
12. **Duplicate migration timestamp `20261030000000`.** Rename one file only if those two have not both been applied yet.
13. **Already-seeded `ORD-20260803-*` rows** stay in the database. Dashboard and orders hide them. Delete them in SQL if the shop should not keep the rows.
14. **Platform Gemini calls** (embeddings, skill extract, sales engine, and others) still put the platform key in the query string. This PR only changed the BYOK validate route.
