# แผนงานถัดไป: บอทขายอัตโนมัติ & การสมัครเริ่มต้นใช้งาน

> เขียนเมื่อ 17 ตุลาคม 2026 หลังรอบแก้ไข PR #1–#9 (ดูสรุปใน [PROJECT_STATUS.md](../../PROJECT_STATUS.md) หัวข้อ "Bot Sales Hardening")
> ทุกข้อด้านล่าง **ตรวจพบจริงจากโค้ดหรือฐานข้อมูล production** ไม่ใช่การคาดเดา — แต่ละข้อระบุไฟล์/หลักฐานไว้ให้ AI หรือนักพัฒนาคนถัดไปหยิบไปทำต่อได้ทันที

## สถานะปัจจุบัน (ยืนยันบน production แล้ว)

- บอทตอบคำถามจากคลังความรู้, สร้างออเดอร์, ออกใบเสนอราคา, ยืนยันใบเสนอราคาเป็นออเดอร์, ส่ง QR, ตรวจสลิป — ทดสอบผ่าน LINE จริงแล้ว
- ราคา/ค่าส่ง/ยอด QR คำนวณจากฐานข้อมูล ไม่เชื่อตัวเลขจาก AI
- ตรวจสลิป: ต้องเป็นออเดอร์ของลูกค้าคนนั้น, ยอดตรง, บัญชีผู้รับเป็นของร้าน, สลิปไม่ซ้ำ — ไม่ผ่านส่งให้แอดมิน
- ข้อความติดตาม (ทวงจ่าย/เตือนนัด/ข้อความที่บอทนัด) ทำงานทุก 5 นาทีผ่าน GitHub Actions
- สมัครใหม่ → onboarding → สร้างร้านและผูกบัญชีถูกต้อง (ทดสอบด้วยบัญชี JackDev)
- ทุกร้านที่เชื่อม LINE มี Channel Secret และผ่านการตรวจลายเซ็น

## ส่วนที่ 1 — บอทตอบคำถาม / จัดการออเดอร์ / ตรวจสลิป

### 🔴 ลำดับ 1 (ควรทำก่อน มีผลกับเงินหรือประสบการณ์ลูกค้าโดยตรง)

**1.1 LINE ส่ง webhook ซ้ำ แล้วบอททำงานซ้ำ**
- ปัญหา: LINE ส่ง event ซ้ำได้เมื่อ webhook ตอบช้าหรือ error (`deliveryContext.isRedelivery`) แต่ `src/app/api/webhook/[shop_id]/route.ts` ไม่เก็บ `webhookEventId` เลย → ออเดอร์/QR/ใบเสนอราคาซ้ำได้
- แนวทาง: ตาราง `processed_webhook_events (event_id PK, shop_id, created_at)` หรือ unique index; insert ก่อนประมวลผล ถ้าชนแปลว่าเคยทำแล้วให้ข้าม
- ต้องมี migration (รันใน Supabase dashboard เอง)

**1.2 รูปทุกรูปถูกตรวจเป็นสลิป**
- ปัญหา: ลูกค้าส่งรูปสินค้าที่อยากได้ → ระบบส่งไปตรวจสลิป → ตอบ "ตรวจสอบสลิปไม่สำเร็จ" ซึ่งสับสน (โค้ดใน `verifySlipAndNotify`)
- แนวทาง: ถ้าลูกค้าไม่มีออเดอร์ค้างจ่าย **และ** ตัวตรวจสลิปอ่านไม่ออก → ตอบกลาง ๆ ("ได้รับรูปแล้วค่ะ สนใจสินค้าชิ้นนี้ใช่ไหมคะ") และไม่ส่งแจ้งเตือนแอดมิน; ตอบว่าตรวจสลิปไม่ผ่านเฉพาะเมื่อมีออเดอร์ค้างจ่าย

**1.3 คำตอบเกิน 5 ข้อความ LINE ปฏิเสธทั้งชุด**
- ปัญหา: `deliverAgentResult` รวมข้อความตอบ + การ์ดสินค้า + QR + ข้อความประกอบไว้ใน Reply API ครั้งเดียว LINE รับได้สูงสุด 5 ข้อความ เกินแล้วลูกค้าไม่ได้อะไรเลย
- แนวทาง: ส่ง 5 ข้อความแรกด้วย Reply ที่เหลือส่งด้วย Push (หรือรวมข้อความ text ที่ติดกัน)

**1.4 ออเดอร์ค้างจ่ายไม่มีวันหมดอายุ และสต็อกไม่คืน**
- ปัญหา: `take_order` ตัดสต็อกทันทีตอนสร้างออเดอร์ (ก่อนจ่าย) ไม่มีการคืนสต็อกเมื่อยกเลิก และออเดอร์ `pending` ค้างตลอดไป
- แนวทาง: งานใน cron เดิม (`processDueFollowUpTasks` หรือ route ใหม่) — ออเดอร์ pending เกิน X ชั่วโมง (ให้ร้านตั้งได้ ค่าเริ่มต้น 24 ชม.) → `cancelled` + คืนสต็อก + ยกเลิก follow-up; ปุ่มยกเลิกในหน้าออเดอร์ต้องคืนสต็อกด้วย

### 🟠 ลำดับ 2

**1.5 สั่งได้ทีละ 1 สินค้าต่อออเดอร์**
- `take_order` รับ `product` เดียว ถ้าลูกค้าสั่ง 2 อย่าง AI ต้องแยกเป็น 2 ออเดอร์ (2 QR)
- แนวทาง: เพิ่ม `items: [{product, qty}]` ใช้ `resolveCatalogProduct` ทีละรายการ (โครงเดียวกับ `create_quotation`)

**1.6 กันสลิปซ้ำด้วยตารางเฉพาะ**
- ตอนนี้ค้นจาก `orders.note` (`[slip-ref:...]`) ใช้ได้แต่ไม่แข็งแรง
- แนวทาง: ตาราง `payment_slips (shop_id, trans_ref, order_id, provider, amount, created_at, UNIQUE(shop_id, trans_ref))`

**1.7 Facebook Messenger ยังไม่มีการตรวจสลิป**
- `src/app/api/webhook/facebook/[shop_id]/route.ts` ไม่จัดการรูปภาพ/สลิปเลย ลูกค้าที่จ่ายผ่าน Facebook ต้องรอแอดมินยืนยันเอง
- แนวทาง: แยก slip flow จาก LINE webhook เป็นโมดูลกลาง (`src/lib/slip/settleSlip.ts`) แล้วเรียกจากทั้ง LINE และ Facebook

**1.8 ทบทวนต้นทุน AI หลังลด prompt (หลัง 20 ต.ค. 2026)**
- ดู `ai_provider_usage.prompt_tokens / message_count` เทียบกับค่าเดิม ~13,000 token/ข้อความ
- ใช้ตัวเลขจริงทบทวนราคาแพ็กเกจ (ประเมินเดิม: ใช้เต็มโควต้าแล้ว Starter/Pro/Agency ขาดทุนกับ Gemini)
- พิจารณาจำกัด token ต่อแพ็กเกจด้วย (ตอนนี้จำกัดเฉพาะจำนวนข้อความ)

### 🟡 ลำดับ 3 (เก็บกวาด)

- **1.9** `routing.targetProvider` คำนวณแล้วไม่ถูกใช้ (`callCurrentStep` เรียก Gemini ก่อนเสมอ) — ลบทิ้งหรือทำให้ใช้งานจริง
- **1.10** รุ่น Claude ในโค้ดเก่า (claude-3-5-*) — อัปเดตหรือถอด Claude ออกจาก fallback ถ้าไม่ใช้
- **1.11** `MASTER_TOOLS` ยังประกาศเครื่องมือที่ไม่มีโค้ด 13 ตัว (ซ่อนไว้ด้วย `UNIMPLEMENTED_TOOLS`) — ทำทีละตัวตามความต้องการจริง (เช่น `track_parcel`, `send_invoice`) หรือลบทิ้ง

## ส่วนที่ 2 — การสมัครและเริ่มต้นใช้งาน

### 🔴 ลำดับ 1

**2.1 ช่วงทดลองใช้ไม่มีวันหมด**
- หลักฐาน: ร้านใหม่ได้ `plan='trial'`, `plan_key='free'`, `trial_expires_at` = +14 วัน แต่ **ไม่มีโค้ดไหนอ่าน `trial_expires_at`** (ค้นทั้ง `src/` แล้ว)
- ผล: ร้านทดลองใช้ได้โควต้าแพ็กเกจ free (500 ข้อความ/เดือน) ไปตลอด
- ต้องตัดสินใจเชิงธุรกิจก่อน: หมด trial แล้ว (ก) บอทหยุดตอบ (ข) ลดเหลือโควต้า free (ค) ให้ใช้ต่อแต่แสดงแจ้งเตือนให้อัปเกรด
- แนวทาง: เช็กใน `getQuotaStatus` (salesAgentEngine) + แบนเนอร์นับถอยหลังในแดชบอร์ด + อีเมลเตือนก่อนหมด 3 วัน

**2.2 ไม่มีขั้นตอนพาตั้งค่าหลังสมัคร**
- หลังกรอกชื่อร้านและเลือกเทมเพลต ร้านเข้าแดชบอร์ดเลย แต่บอทยังขายอัตโนมัติไม่ได้จนกว่าจะตั้งค่า 5 อย่าง:
  1. เชื่อม LINE OA (Channel Access Token + **Channel Secret** + ตั้ง Webhook URL ใน LINE Console)
  2. ใส่สินค้า (บอทสร้างออเดอร์/ใบเสนอราคาได้เฉพาะสินค้าที่อยู่ในระบบ)
  3. ใส่เลขพร้อมเพย์หรือบัญชีธนาคาร (ไม่มี = ส่ง QR ไม่ได้ และสลิปทุกใบต้องให้แอดมินตรวจ)
  4. ใส่ LINE ID แอดมิน (ไม่มี = ไม่มีใครได้รับแจ้งเตือนออเดอร์/สลิปรอตรวจ)
  5. ใส่คลังความรู้อย่างน้อย 5–10 ข้อ
- แนวทาง: การ์ด "ตั้งค่าร้านให้พร้อมขาย" บนแดชบอร์ด แสดงแต่ละข้อพร้อมสถานะ ✓/✗ และปุ่มไปหน้าที่ต้องตั้ง คำนวณจากข้อมูลจริงในตาราง (ไม่ต้องเก็บ state เพิ่ม); ตั้ง `onboarding_completed = true` เมื่อครบ (คอลัมน์นี้มีอยู่แต่ยังไม่มีโค้ดใช้)

**2.3 ฟอร์มเชื่อม LINE ไม่บังคับ Channel Secret**
- `src/app/dashboard/settings/ChannelsSettingsForm.tsx` ใส่ Token อย่างเดียวได้ → webhook ของร้านนั้นไม่ถูกตรวจลายเซ็น (มี log เตือนเท่านั้น)
- แนวทาง: บังคับใส่คู่กัน + ตรวจรูปแบบ (32 ตัวอักษร hex) + ปุ่ม "ทดสอบการเชื่อมต่อ" ที่เรียก LINE API ด้วย Token จริง และแสดง Webhook URL ให้คัดลอก

### 🟠 ลำดับ 2

**2.4 ความหมายของ trial กับ free ยังไม่ชัด**
- ร้านใหม่: `plan='trial'` แต่ `plan_key='free'`; ป้ายแสดง TRIAL ส่วนโควต้าใช้ของ free — กำหนดให้ชัดว่า trial คือแพ็กเกจไหน (เช่น ทดลองแพ็กเกจ Pro 14 วัน) แล้วตั้ง `plan_key` ให้ตรง

**2.5 บัญชีที่ยังไม่ผูกร้าน 2 บัญชี**
- หลัง PR #8 บัญชีเหล่านี้จะถูกพาไป onboarding เมื่อเข้าแดชบอร์ด หนึ่งในนั้นไม่มีอีเมล — ตรวจว่าเป็นบัญชีจริงหรือขยะ แล้วลบหากไม่ใช้
